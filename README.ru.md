Кроссплатформенный вычислительный бенчмарк CPU и GPU. Запуск без аргументов
прогоняет фиксированный набор целочисленных нагрузок на одном потоке CPU, на всех
потоках CPU и на каждом доступном GPU-API (CUDA, Vulkan). Каждый результат
сверяется с golden-значениями, зашитыми в бинарь. В конце печатаются баллы и
пишется JSON-отчёт, пригодный для лидерборда. Название — от исходной нагрузки:
обезьяны печатают случайный текст, пока не наберут эталонную строку.

```text
$ monkey_bench
monkey_bench 1.0.0 (…) · suite v1 · standard
CPU:  Apple M4 Pro · 14 threads (10P + 4E) · 24.0 GiB · macOS 27.0 arm64
GPU:  Apple M4 Pro · Vulkan (MoltenVK 1.4.2, u64 native) · init 0.04 s
…
Test                      CPU-ST          CPU-MT      GPU Vulkan
monkey-random         1055 ±0.4%      1001 ±0.1%      1000 ±0.1%
monkey-brute          1034 ±0.3%       999 ±0.1%       998 ±0.2%

mr-prime64            1001 ±0.0%       999 ±0.2%       999 ±0.1%
Category                    1033            1000             998

CPU score:        1016   geomean(CPU-ST, CPU-MT)
GPU score:         998   best API: GPU Vulkan
Overall score:    1010   geomean(CPU-ST, CPU-MT, GPU)
```

## Быстрый старт

Скачайте архив для своей платформы со страницы релизов и запустите:

```bash
./monkey_bench                       # стандартный suite: 3 прогона на тест, ~4 мин
./monkey_bench --quick               # 1 прогон на тест, ~1.5 мин (та же работа, сравнимо)
./monkey_bench run --json result.json
./monkey_bench verify                # проверить каждое ядро на каждом бэкенде
```

- **Windows / Linux x86_64:** встроены CUDA (NVIDIA) и Vulkan (любой GPU).
- **Linux arm64:** Vulkan.
- **macOS arm64:** Vulkan через MoltenVK — `libMoltenVK.dylib` лежит рядом с
  бинарём. Gatekeeper помещает распакованные бинари в карантин; выполните
  `xattr -dr com.apple.quarantine .` в папке.

Нужен только обычный драйвер GPU. Без драйвера Vulkan или CUDA бинарь всё равно
прогоняет CPU-категории и объясняет, почему GPU недоступен. Если сломанный
драйвер GPU роняет процесс, задайте `MONKEY_DISABLE_VULKAN=1` — пойдут только
CPU-категории.

Для стабильного результата закройте тяжёлые приложения, а ноутбук подключите к
зарядке.

## Что измеряет suite v1

Четыре теста. Каждый обрабатывает фиксированный диапазон единиц работы `[0, N)`,
и все единицы примерно равны по стоимости. Балл считается из времени, за которое
выполнена эта фиксированная работа. N подобран по категориям так, чтобы на
эталонной машине каждый тест шёл 3–10 с.

| Тест | Единица работы | Что нагружает | С чем сверяется результат |
| --- | --- | --- | --- |
| `monkey-random` | случайный кандидат из 43 символов для *«The quick brown fox jumps over the lazy dog»* (алфавит 28) из Philox4x32-10; результат — длина совпавшего префикса | пропускная способность 32-битных умножений и xor, короткие циклы с ветвлением по данным | golden checksum |
| `monkey-brute` | индекс в системе счисления 28, дополненный нулями до 43 разрядов; результат — длина совпавшего суффикса | пропускная способность 64-битного деления | golden checksum |
| `bbp-pi` | блок из 256 членов ряда Бэйли–Борвейна–Плаффа для hex-цифр π около позиции 10⁶ | 32-битное модульное возведение в степень по Монтгомери, деление столбиком, параллелизм на уровне инструкций | 8 hex-цифр каждой позиции против встроенного `reference/pi_hex.txt` и golden checksum |
| `mr-prime64` | детерминированный тест Миллера–Рабина одного нечётного числа больше 2⁶² | 64-битное умножение по Монтгомери (`mulhi`), ветвистый код (дивергенция SIMD на GPU) | golden-число простых и checksum, перепроверенные сегментированным решетом |

Вся арифметика целочисленная. Она определена так, что у каждой единицы работы
ровно один бит-в-бит одинаковый результат на любом CPU и GPU. Плавающей точки
нет: результаты FP64 различаются между устройствами, а на Apple GPU FP64 нет
вовсе.

`monkey_bench list` печатает точный объём работы по категориям и эталонные
времена.

## Баллы и как их читать

- **Балл теста** = `1000 × t_ref / t`. Здесь `t` — медиана времени прогонов, а
  `t_ref` — время на эталонной машине (Apple M4 Pro, 10P + 4E, macOS 27.0, GPU
  через MoltenVK 1.4.2). Балл 2000 означает, что тест прошёл вдвое быстрее, чем
  на эталоне.
- **Балл категории** — геометрическое среднее её четырёх тестов. Категории:
  CPU-ST (один поток), CPU-MT (все логические потоки) и GPU, которая
  оценивается отдельно для каждого доступного API (GPU CUDA, GPU Vulkan). У всех
  API одна и та же работа и одно и то же `t_ref`.
- **CPU score** = geomean(CPU-ST, CPU-MT). **GPU score** — лучший из GPU-API.
- **Итог (Overall)** = geomean(CPU-ST, CPU-MT, GPU). На машине без GPU итог не
  считается: там он был бы несравним. В отчёте такой прогон помечен `partial`.
- **±x %** рядом с баллом — коэффициент вариации времени прогонов. Выше 3 % тест
  помечается `unstable` (`*`). Балл засчитывается, но результат шумный:
  тротлинг, фоновая нагрузка, энергосбережение.
- **INVALID** — checksum, число простых или цифра π не совпали с golden. У теста
  нет балла; нет его и у категории, и у итога.
- **Сравнимость.** Баллы сравнимы только в пределах одной `suite_version`.
  Любое изменение ядра, размера работы или golden её поднимает. Кроме того,
  отчёт помечает как несравнимые прогоны custom и stress, а также debug-сборки
  и сборки с `-march=native`.

Геометрическое среднее не даёт одному выдающемуся тесту задавить категорию.
Ускорение одного из четырёх тестов вдвое поднимает категорию на 19 %, а не на
25 %.

## Методология

**Фиксированная работа, а не «сколько успели за N секунд».** У каждого теста
фиксированное число единиц работы, а часы измеряют, сколько они заняли. Раньше
бенчмарк считал операции в секунду за заданное время. Стоимость операции там
росла с counter'ом (Miller–Rabin, BBP), и результат зависел от длительности и
числа потоков.

**Одна сессия на устройство.** Потоки CPU и контексты GPU создаются один раз.
Дальше для каждого теста и категории движок выполняет:

1. **Прогрев** 2 с (1 с в `--quick`). Частоты выходят на рабочие, а размер чанка
   подстраивается под ~15 мс на CPU-чанк и ~30 мс на GPU-диспатч. Это далеко от
   лимита TDR в Windows (2 с), а стоп срабатывает не позже чем через один чанк.
2. **Замеры**: 3 в `--standard`, 1 в `--quick`. Все воркеры стартуют по общему
   барьеру. Время идёт по `steady_clock` до завершения последнего чанка.
   Инициализация устройств выводится отдельно (`init_time_s`) и в замер не
   входит.

**Общий диспетчер чанков.** Работа раздаётся чанками — один атомарный
compare-and-swap на чанк, а не на операцию. Потоки CPU и GPU в `--all` делят
один диспетчер: ничего не считается дважды, а быстрые устройства просто берут
больше чанков.

**Checksum, не зависящий от порядка.** Результат единицы `i` попадает в сумму
`Σ fmix64(fmix64(i) ⊕ r) mod 2⁶⁴` (финализатор splitmix64; единицы с «пустым»
результатом `r = 0` вклада не дают). Сумма не зависит от числа потоков, размера
чанка и порядка исполнения, поэтому потоки CPU и диспатчи GPU могут складывать
свои части. Отдельно сверяются число обработанных единиц и число непустых
результатов.

**Одни и те же операции на каждом бэкенде.** Каждый workload — одно
header-only ядро (`src/workloads/*_kernel.h`, `__host__ __device__` для CUDA) с
построчным GLSL-портом (`src/shaders/`). GLSL собирается в двух вариантах:
нативный `uint64_t` (`shaderInt64`) и эмуляция на `uvec2` для устройств без
этой фичи. `test_parity` и `monkey_bench verify` проверяют, что CPU, CUDA и оба
варианта Vulkan возвращают одинаковые результаты на фиксированных диапазонах.

**Гибридные CPU.** На macOS потоки бенчмарка идут с наивысшим QoS, поэтому
CPU-ST остаётся на производительном ядре. На Linux и Windows потоки не
закреплены, решает планировщик ОС. В отчёт записывается число P- и E-ядер.

**Стресс-режим.** `run --stress -d 60` повторяет фиксированное окно каждого
теста 60 с на тест и категорию и проверяет каждый завершённый проход. Он
выводит пропускную способность во времени и `throttle_ratio` — отношение
пропускной способности последних 10 % времени к первым 10 %. Баллов не даёт;
нужен для анализа тротлинга и стабильности.

**Разброс итога между прогонами** на эталонной машине описан в
[BENCH.md](BENCH.md).

## Команды

```text
monkey_bench [run] [options]          прогнать suite и напечатать баллы
monkey_bench list                     список тестов suite
monkey_bench info                     система, сборка и вычислительные устройства
monkey_bench verify [options]         проверить каждое ядро на каждом бэкенде
monkey_bench custom [file] [options]  свой workload: только ops/s, без сравнения
monkey_bench <file> [options]         старый синтаксис, то же, что custom
```

| Опция `run` | Значение |
| --- | --- |
| `--standard` / `--quick` / `--stress` | 3 прогона на тест (по умолчанию), 1 прогон или стресс по времени |
| `--cpu` / `--gpu` / `--all` | CPU-категории, GPU-категории или всё плюс информационная строка CPU+GPU |
| `--gpu-api auto\|cuda\|vulkan` | какие GPU-API тестировать (по умолчанию все доступные) |
| `--test NAME` | только этот тест (можно повторять); балл категории требует всех четырёх |
| `-d, --duration SEC` | стресс: секунд на тест и категорию (по умолчанию 30) |
| `--json FILE` | записать JSON-отчёт v2 (`-` — в stdout) |
| `--vk-allow-cpu` | разрешить программные Vulkan-устройства вроде Mesa lavapipe |

Коды выхода: `0` — успех; `1` — ошибка аргументов или бэкенда (прогон
останавливается с сообщением, а не зависает); `2` — результат не совпал с
golden.

## JSON-отчёт

`--json FILE` пишет отчёт по схеме
[`bench_output.schema.json`](bench_output.schema.json) (схема v2). CI проверяет
его через `check-jsonschema`. В отчёте:

- `schema_version`, `suite_version`, `mode`, `timestamp`;
- `binary`: версия, git sha, компилятор, флаги, тип сборки;
- `system`: ОС, ядро, модель CPU, физические/логические/P/E-ядра, RAM;
- `devices`: API, имя, производитель, драйвер, вычислительные блоки, режим
  64-битной арифметики, время инициализации;
- `tests[]`: время прогонов, медиана/min/max/CV, ops/s, checksum и ожидаемый
  checksum, валидность, балл, размер чанка, распределение работы между CPU и
  GPU;
- `scores`: категории, CPU, GPU, итог;
- `flags`: `comparable`, `custom`, `debug_build`, `native_arch`,
  `portable_arith`, `invalid`, `unstable`, `partial`.

Checksum пишется hex-строкой: JSON-числа теряют точность выше 2⁵³.

## Сборка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build
```

- **Vulkan** встраивается, если найдены заголовки Vulkan и `glslangValidator`
  (Vulkan SDK; на Linux — `libvulkan-dev glslang-tools`; на macOS —
  `brew install vulkan-headers vulkan-loader glslang molten-vk`). Loader Vulkan
  открывается в рантайме, поэтому бинарь от него не зависит.
- **CUDA** встраивается, если найден CUDA Toolkit (11+); рантайм линкуется
  статически.

| Опция CMake | По умолчанию | Значение |
| --- | --- | --- |
| `USE_CUDA` / `USE_VULKAN` | `ON` | включить бэкенд, если найден его SDK |
| `MONKEY_NATIVE_ARCH` | `OFF` | `-march=native`; такие сборки помечаются как несравнимые |
| `MONKEY_PORTABLE_ARITH` | `OFF` | принудительно переносимые 32-битные пути ядер (как на MSVC и в GLSL); CI гоняет тесты и так |
| `MONKEY_BUILD_TESTS` | `ON` | юнит-тесты Catch2, тесты паритета бэкендов и смоук-тесты CLI |

`tools/suite_gen.cpp` (`cmake --build build --target monkey_suite_gen`)
пересчитывает golden-значения suite.

CI собирает и тестирует на Linux x86_64 и arm64 (Vulkan через Mesa lavapipe),
Windows x86_64 (MSVC), macOS arm64 (MoltenVK) и в сборке с переносимой
арифметикой. Ещё он компилирует CUDA-бэкенд.

## Исходный поиск обезьян (режим custom)

Теорема о бесконечных обезьянах: случайная последовательность символов,
набираемая бесконечно долго, почти наверняка содержит любой заданный текст.
Случайная строка длины `L` над алфавитом из `N` символов совпадает с эталоном с
вероятностью `1/N^L`. Режим custom ищет такое совпадение для вашего файла,
пока не найдёт его или не выйдет время:

```bash
./monkey_bench custom reference.txt -m random -d 10   # случайные кандидаты, 10 с
./monkey_bench custom reference.txt -m brute -gpu     # перебор пространства на GPU
./monkey_bench reference.txt -all -d 10               # старый синтаксис: CPU + GPU вместе
./monkey_bench custom -w bbp -d 10                    # ядра suite по времени
```

Алфавит — множество различных UTF-8 символов эталона, а горячий путь сравнивает
индексы алфавита. Поэтому скорость зависит только от размера алфавита и длины
строки. Письменность (латиница, кириллица, CJK, эмодзи) и число байт на символ
значения не имеют. Перебор использует 64-битный индекс: эталон, чей код больше
2⁶⁴, перебором не найти, и программа об этом сообщает. Режим custom выдаёт ops/s
по завершённым чанкам и никогда не сравнивается с баллами suite.

## Ограничения

- **Только целочисленные вычисления.** Suite нагружает целочисленное АЛУ,
  умножение, деление и ветвления. Пропускную способность памяти, кэши, плавающую
  точку и ввод-вывод он не измеряет. Это не универсальная замена Geekbench или
  SPEC.
- **Одна эталонная машина.** Баллы считаются относительно Apple M4 Pro. Его GPU
  работает через MoltenVK (Vulkan поверх Metal); нативный Metal вне скоупа, и
  накладные расходы MoltenVK могут немного занижать Apple GPU.
- **Фиксированная работа на GPU.** GPU-тесты рассчитаны на ~5 с на эталонном GPU.
  Медленный встроенный GPU идёт пропорционально дольше, а программный Vulkan
  (lavapipe) — часами, поэтому в CI GPU проверяется через `verify`, а не полным
  прогоном.
- **CUDA в CI проверяется только компиляцией.** При разработке suite v1 не было
  GPU NVIDIA. На машине с NVIDIA один раз запустите `monkey_bench verify`: он
  сверит результаты CUDA с golden.
- **Чувствительность к микроархитектуре — намеренная.** Например,
  `monkey-brute` зависит от пропускной способности 64-битного деления, которая
  различается между ядрами CPU в разы и эмулируется на GPU.
- **Ноутбуки и гибридные CPU.** Тепловые лимиты и планирование на гибридных CPU
  вне macOS добавляют шум. Следите за флагом `unstable`, а тротлинг смотрите
  через `--stress`.
